# Share Link Integrity — Integration Tests (Phase 2) Implementation Plan

## Overview

Add integration tests for Risk #2 (expired share token still returns canvas data) and Risk #3 (share-token recipient can reach write endpoints). Both risks are already correctly implemented; these tests are regression guards that prove the protection holds and would catch any future refactor that removes it.

## Current State Analysis

Phase 1 (testing-infra-access-control) shipped the full test infrastructure: Vitest + `@cloudflare/vitest-pool-workers`, the `SELF.fetch()` pattern, `supabaseAdmin` for service-role fixture setup, and the `createTestUser` / `createTestCanvas` / `getAuthCookies` helpers. No new tooling is needed for Phase 2.

The `tests/helpers/setup.ts` file has user and canvas helpers but no share-link helper. Phase 2 adds `createTestShareLink` and `deleteTestShareLink` to that file, then writes a single new integration test file covering both risks.

### Key Discoveries

- **API route vs. page route**: The oracle for Risk #2 requires a non-200 status. `GET /api/share/[token]` returns `404` for expired tokens. `GET /share/[token]` (the Astro page) returns `200` with error HTML — it never sends a non-200. Tests must target the API route. (`src/pages/api/share/[token].ts:26-33`)
- **Dual-layer expiry enforcement**: RLS (`supabase/migrations/20260607000000_canvas_schema.sql:100-103`) makes expired rows invisible to the anon client; `isExpired()` (`src/pages/api/share/[token].ts:8-13`) is the application-layer backstop. One integration test exercises both simultaneously.
- **Auth guard fires before any DB access**: Every write handler's first operation is `if (!context.locals.user) return 401` (`src/pages/api/canvases/[id].ts:29-31, 53-55`). The Risk #3 tests need no Cookie header and require no share link fixture.
- **Cascade deletion**: `share_links` has `ON DELETE CASCADE` on `canvas_id`. Deleting the canvas in `afterAll` automatically removes associated share links — no explicit `deleteTestShareLink` call is needed in teardown, but the helper is provided for standalone use.
- **Token generated by DB default**: The `token` column has `DEFAULT encode(extensions.gen_random_bytes(32), 'hex')`. `INSERT` only needs `canvas_id` and optionally `expires_at`; the token is retrieved via `.select("id, token")`.

## Desired End State

- `tests/helpers/setup.ts` exports `createTestShareLink` and `deleteTestShareLink`.
- `tests/integration/share-link-integrity.test.ts` exists with four passing tests across two `describe` blocks.
- `npm run build && npm test` exits 0 with all tests (Phase 1 + Phase 2) passing.
- `context/foundation/test-plan.md §6.3` documents the public route test pattern for future contributors.
- Phase 2 row in `test-plan.md §3` shows status `complete`.

## What We're NOT Doing

- No tests for the Astro page route (`GET /share/[token]`) — it returns 200 for expired tokens (by design, error shown in HTML) and is not the enforcement point.
- No tests for pin-protected share links — `pin_hash` column exists but pin enforcement is out of scope for Phase 2.
- No coverage of every write handler individually — `PATCH` + `DELETE` on `/api/canvases/[id]` prove the pattern; all 8 handlers use the identical guard.
- No new test infrastructure or npm dependencies — Phase 1 already bootstrapped everything.
- No migration or schema change — the `share_links` table and its RLS policies are in place.

## Implementation Approach

Two-phase delivery plus a final documentation step:

1. Extend the existing helpers file with share-link fixture functions.
2. Write the test file with two `describe` blocks — one per risk, each with its own `beforeAll`/`afterAll` for clear isolation.
3. Update the cookbook and advance the rollout state.

## Critical Implementation Details

**API endpoint target**: Always use `http://localhost/api/share/{token}` in test assertions, not `http://localhost/share/{token}`. The API route returns `404` on expired/invalid tokens; the page route returns `200` with HTML. Tests that hit the page route would pass against a broken server.

**CSRF and GET requests**: The `Origin: http://localhost` header is required for mutations (POST/PATCH/DELETE) due to Astro's `security.checkOrigin` default. It is **not** required for `GET /api/share/{token}`, which is a read-only public endpoint. Include Origin only on the Risk #3 write tests.

**cascade vs. explicit cleanup**: In `afterAll`, call `deleteTestCanvas` and `deleteTestUser` only. The `share_links` rows are removed by cascade. Calling `deleteTestShareLink` in teardown is redundant and risks a double-delete if the canvas was already deleted; omit it from `afterAll`.

## Phase 2: Write share-link-integrity integration tests

### Overview

Create `tests/integration/share-link-integrity.test.ts` with two `describe` blocks — one per risk. Risk #2 has two test cases (expired token + valid token happy path); Risk #3 has two test cases (unauthenticated PATCH + DELETE). All four tests use `SELF.fetch()` against the workerd runtime.

### Changes Required

#### 1. `tests/integration/share-link-integrity.test.ts`

**File**: `tests/integration/share-link-integrity.test.ts` (new file)

**Intent**: Prove the expiry enforcement and write-endpoint auth guard in a single test file, following the Phase 1 `access-control.test.ts` structure.

**Contract — `describe("Risk #2 — expiry rejection")`**:

`beforeAll` creates one test user, one canvas, one expired share link (past `expires_at`), and one valid share link (`expires_at = null`). `afterAll` calls `deleteTestCanvas` (cascades share links) then `deleteTestUser`, both with `.catch(() => undefined)`.

Test cases:

- `"GET /api/share/{token} with expired token returns 404"` — sends `SELF.fetch("http://localhost/api/share/{expiredToken}")` with no headers. Asserts `response.status === 404` and that `await response.text() === ""` (the handler returns `new Response(null, { status: 404 })`).
- `"GET /api/share/{token} with valid token returns 200 with canvas and shareLink"` — sends the same fetch with the valid token. Asserts `response.status === 200`, parses the JSON body, and asserts that `body.canvas` is a non-null object and `body.shareLink` is a non-null object.

**Contract — `describe("Risk #3 — write access without auth session")`**:

`beforeAll` creates one test user and one canvas (no share link needed). `afterAll` mirrors Risk #2 teardown pattern.

Test cases:

- `"PATCH /api/canvases/{id} without auth session returns 401"` — sends `SELF.fetch` with `method: "PATCH"`, headers `{ "Content-Type": "application/json", Origin: "http://localhost" }` (no `Cookie`), and the 9-key `blocks` body from the cookbook schema note. Asserts `response.status === 401`.
- `"DELETE /api/canvases/{id} without auth session returns 401"` — sends `SELF.fetch` with `method: "DELETE"`, header `{ Origin: "http://localhost" }` (no `Cookie`). Asserts `response.status === 401`.

## Testing Strategy

### Integration Tests

Four tests in `tests/integration/share-link-integrity.test.ts`:

- **Risk #2 expired**: Seed with past `expires_at`; assert 404 + empty body (exercises RLS invisible-row + app `isExpired()` path)
- **Risk #2 valid**: Seed with `expires_at = null`; assert 200 + `{ canvas, shareLink }` in body (proves fixture is correctly wired and valid links work)
- **Risk #3 PATCH**: No Cookie; assert 401 (proves auth guard fires before any DB access)
- **Risk #3 DELETE**: No Cookie; assert 401 (same guard on delete path)

### No Mutation Testing Needed

The guards being tested are simple boolean gates (`if (!user) return 401`, `if (shareError || isExpired(...)) return 404`). A survived mutant on a direct comparison here would change a gate condition — visible to any of these four tests. No Stryker run is warranted for this phase.
